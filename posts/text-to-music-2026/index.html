Text-to-music in 2026: models, reward models and DPO

October 31, 2026 · 16 min read · music generation · alignment · reward models

Three ideas carry most of text-to-music today: a codec language model that writes music as discrete tokens, a reward model that judges what it wrote, and preference alignment that folds those judgments back into the generator. This post builds all three from a handful of parts, with the tensor shape written next to every step. It follows MusicGen (2023) to HeartMuLa (2026), CLAP to the CMI reward model, and best-of-N to DPO.

Notation. [paper] marks a fact stated by the cited source. [illustrative] marks a number or structure chosen to explain an idea, not the model's actual setting. The code is shape-annotated pseudocode, not a runnable implementation.

1. The parts

Audio is a long list of numbers

# mono, 32 kHz, 30 seconds
wav: float[B, 1, S]        # S = 32_000 * 30 = 960_000;  B = batch (songs processed together)

A codec turns audio into discrete tokens

A language model works on discrete tokens, like words from a vocabulary, so the waveform has to become tokens first. MusicGen uses the EnCodec codec [1] [paper]. Its encoder downsamples by 640, turning every 640 samples into one vector:

z = encoder(wav)           # float[B, D, T]
# T = 960_000 / 640 = 1500 frames (50 frames per second);  D = latent size [illustrative: 128]

Then residual vector quantization (RVQ) replaces each continuous vector with \(K\) integers. There are \(K\) codebooks of 2048 vectors each. The first codebook picks the vector nearest to \(z\); the residual \(r = z - \text{chosen}\) goes to the second codebook, which picks the vector nearest to \(r\); and so on. Each codebook corrects what the previous ones missed, so later codebooks carry finer detail.

def rvq_encode(z):                 # z: float[B, D, T]
    residual, codes = z, []
    for k in range(K):             # MusicGen: K = 4 [paper]
        dist = ((residual[..., None] - codebook[k]) ** 2).sum(1)   # [B, T, 2048]
        idx = dist.argmin(-1)                                      # int[B, T]
        residual = residual - codebook[k][idx]
        codes.append(idx)
    return stack(codes, dim=1)     # int[B, K, T] = [B, 4, 1500], values 0..2047

Decoding sums the chosen vectors across codebooks and runs the decoder back to a waveform. To the model, thirty seconds of music is a 4 × 1500 table of integers.

An autoregressive language model

The model predicts one step at a time and appends its prediction to the input. The log-probability of a whole sequence is the sum of the per-step log-probabilities of the tokens that were chosen:

\[ \log p(c \mid \text{text}) = \sum_{t=1}^{T} \log p(c_t \mid c_{<t}, \text{text}) \] 
logits = lm(c[:, :, :t], text_emb)     # float[B, K, V], V = 2048
logp = log_softmax(logits, -1)         # log-probability of each candidate token

DPO in section 4 reuses exactly this sum.

Embeddings, cosine similarity and the sigmoid

An encoder maps a clip or a sentence to a fixed-length vector \(e \in \mathbb{R}^D\). Cosine similarity \(\cos(a, b) = a \cdot b / (\lVert a\rVert \lVert b\rVert) \in [-1, 1]\) measures how closely two vectors point the same way. The sigmoid \(\sigma(x) = 1/(1 + e^{-x})\) squashes any real number into \((0, 1)\), with \(\sigma(0) = 0.5\) and \(\sigma(3) \approx 0.95\).

2. Models: codec language models, MusicGen to HeartMuLa

MusicGen (2023)

Text goes through a T5 encoder to text_emb: float[B, L, 768], and a transformer decoder reads it through cross-attention while generating codec tokens [2] [paper].

Delay pattern. Each frame has four tokens. Predicting them one per step would take 4 × 1500 steps. MusicGen instead shifts codebook \(k\) back by \(k\) steps, so each step emits four tokens at once, about \(T + K - 1 = 1503\) steps in total.

Classifier-free guidance (CFG). Each step runs the model twice, with and without the text, and amplifies the difference (the appendix explains why this works):

\[ \text{logits} = \text{logits}_{\text{uncond}} + \gamma\,(\text{logits}_{\text{cond}} - \text{logits}_{\text{uncond}}), \qquad \gamma \approx 3 \] 
def musicgen_generate(prompt, n_candidates=8, seconds=30):
    text_emb = repeat(t5(prompt), n_candidates)   # [8, L, 768]
    T = 50 * seconds                              # 1500
    c = empty_int(8, 4, 0)                        # [B=8, K=4, 0]
    for t in range(T + 3):                        # delay pattern
        x = concat([c, c])                        # CFG: with and without text, stacked to 2B = 16 rows
        lg = lm(x, concat([text_emb, null_emb]))  # [16, 4, 2048], with a KV cache
        lg = lg[8:] + 3.0 * (lg[:8] - lg[8:])     # [8, 4, 2048]
        nxt = sample(softmax(lg / temperature))   # int[8, 4]
        c = append(c, nxt)                        # [8, 4, t+1]
    return encodec.decode(undelay(c))             # float[8, 1, 960_000]

This is the loop my earlier post on MusicGen decoding takes apart. Best-of-N pruning hooks in at t = 500 and t = 1000 (10 s and 20 s): decode c[:, :, :t], score it with CLAP, and cut the batch from 8 to 4, then 4 to 2.

HeartMuLa (2026): what changed

HeartMuLa [3] is an open family of music foundation models [paper]. The released model has 3B parameters; the paper reports clear gains at 7B, which was not released. It conditions on lyrics, style tags and a reference clip. Four things differ from MusicGen.

(a) The codec: acoustic versus semantic tokens

# ===== MusicGen: EnCodec, purely acoustic compression =====
wav = float[B, 1, 32_000 * 30]        # 32 kHz mono
codes = rvq(conv_encoder(wav), K=4, V=2048)   # int[B, 4, 1500], 50 Hz
wav_hat = conv_decoder(codes)         # convolutions reconstruct the waveform directly

# ===== HeartMuLa: HeartCodec, semantic compression + generative decoding =====
wav = float[B, 2, 48_000 * 30]        # 48 kHz stereo
f1 = Whisper(wav)                     # (1) three frozen pretrained models: speech and lyric content
f2 = WavLM(wav)                       #     speech features (layers 6-9 averaged)
f3 = MuEncoder(wav)                   #     music features (layer 11 semantic, layer 2 acoustic)
f = Linear(concat(resample_to_25Hz([f1, f2, f3])))          # [B, 750, C]
q = transformer(insert_query_every_2(f))[:, query_positions]  # (2) one learned query per 2 frames: 12.5 Hz, [B, 375, C]
codes = rvq(q, K=8, V=8192)           # int[B, 8, 375]
latent = flow_matching_DiT(codes, steps=10)   # (3) ~1.5B flow-matching DiT regenerates detail; reflow-distilled 50 -> 10 steps
wav_hat = sq_codec_decoder(latent)    # [B, 2, S]
EnCodecHeartCodec
Frame rate50 Hz12.5 Hz
Per frame4 codebooks × 20488 codebooks × 8192
What a token recordsWaveform detailSemantics: lyrics, melody, style
DecoderConvolutional, reconstructs~1.5B generative model, fills in detail

The trade-off: the more abstract the tokens, the shorter the sequence and the easier it is for the language model to learn, but decoding now has to generate detail rather than reconstruct it.

(b) The language model: delay pattern versus global/local

# ===== MusicGen: one transformer + delay pattern =====
for t in range(T + K - 1):                  # 30 s: 1503 steps
    logits = lm(c[:, :, :t], text_emb)      # [B, 4, 2048]: one big model emits all 4 codebooks
    c = append(c, sample(logits))

# ===== HeartMuLa: global (Llama 3.2, 3B) + local (300M) =====
for t in range(T):                          # 30 s: 375 steps
    frame_emb = [sum(embed[k](codes[:, k, s]) for k in range(8)) for s in range(t)]  # sum of 8 token embeddings
    h = global_tf(cat([cond_prefix, frame_emb]))[:, -1]   # [B, d]
    frame = [sample(head0(h))]              # the big model predicts only codebook 0, the coarsest
    for k in range(1, 8):                   # the small model fills in codebooks 1-7 in order
        frame.append(sample(local_tf(h, frame)))
    codes = append(codes, stack(frame))     # [B, 8, t+1]

MusicGen has one large model handle every codebook at every step; the delay pattern only staggers them. HeartMuLa splits the work: the large model decides roughly what this moment should be, so the expensive long-range attention happens only at the frame level, and a small model fills in detail.

(c) Conditioning: cross-attention versus a prefix

# MusicGen: a separate T5 encoder, read by cross-attention in every decoder layer
text_emb = T5(prompt)                        # [B, L, 768]

# HeartMuLa: everything becomes a prefix in the same sequence as the music tokens
c_lyrics = embed(llama_tok("[verse] ... [chorus] ..."))       # section markers kept
c_tag = embed(llama_tok("<tag> jazz, piano, female </tag>"))
c_ref = proj(MuQ_MuLan(ref_audio_10s))       # reference clip, dropped 50% of the time in training
cond_prefix = cat([c_ref, c_tag, c_lyrics])

During training, tags are sampled per category (genre 0.95, timbre 0.5, mood 0.325, …) so the model gets used to incomplete prompts. The reference clip is embedded with MuQ-MuLan [4], the same encoder CMI-RM uses below, which the paper chose because it carries no singer-timbre information [paper].

(d) Training: four stages, ending in DPO

  1. Warm-up: 30-second segments with lyrics and reference audio, on a 10,000-hour subset.
  2. Pretraining: full songs and all three conditions, 100,000 hours, 64 A100s.
  3. Supervised fine-tuning: 15,000 hours filtered with AudioBox and SongEval; the loss on codebook 0 is up-weighted (\(\lambda_0 = 2.0\)).
  4. DPO: four songs per prompt; three reward signals each build their own preference pairs and train their own DPO model (\(\beta = 0.1\), learning rate \(10^{-7}\)); the three models' weights are merged linearly [paper].
pairs_style = margin(MuQ_similarity) > 0.12                           # is the style right?
pairs_lyrics = margin(phoneme_error_rate) > 0.1                       # are the lyrics sung correctly?
pairs_quality = margin(SongEval) > 0.5 and margin(AudioBox_avg) > 0.8  # does it sound good?
# DPO's log pi(y) splits into a global term (codebook 0) and a local term (codebooks 1-7), optimizable separately

Inference uses CFG 1.5, temperature 1.0 and top-k 50. The paper also trains HeartCLAP: both towers initialized from MuQ-MuLan, projected to 1024 dimensions, symmetric InfoNCE on a million music–description pairs. On WikiMT-X text-to-music retrieval it reports R@1 of 4.37, against 2.24 for MuQ-MuLan and 0.71 for LAION-CLAP [paper].

Why 12.5 Hz matters

LengthMusicGen, 50 HzHeartMuLa, 12.5 Hz
30 s1,503 large-model steps375 large-model steps + 375 × 7 small-model steps
4 min12,003 large-model steps3,000 large-model steps + 21,000 small-model steps

Self-attention cost grows with \(T^2\), so at four minutes the large model does roughly \((12000/3000)^2 = 16\) times less attention work. The small model takes more steps, but each looks only inside one frame (at most eight tokens), which is cheap. A low frame rate plus hierarchical prediction is the main reason whole songs of two to four minutes became practical.

3. Scoring: from CLAP to reward models

How CLAP is trained

Take a batch of \(N\) (clip, description) pairs. Two encoders embed each side and form an \(N \times N\) similarity matrix whose diagonal holds the true pairs [5]:

a = normalize(audio_enc(audio))   # [N, D]  [illustrative: D = 512]
t = normalize(text_enc(text))     # [N, D]
S = a @ t.T / tau                 # [N, N]: S[i, j] = similarity of clip i and sentence j
loss = (cross_entropy(S, arange(N)) + cross_entropy(S.T, arange(N))) / 2   # the diagonal should win each row and column

At inference, score = cos(audio_enc(clip), text_enc(prompt)) gives one number.

CLAP's blind spot. It learns which sentence goes with this clip, not which of two clips is better. Two "upbeat piano jazz" clips, one lovely and one grating, can score about the same. That is why CLAP is only an unvalidated proxy for quality, as my best-of-N post discusses.

Reward models learn from comparisons, not scores

People cannot reliably say "this one is a 7.3", but they can say "A is better than B". So the data is pairs:

pair = {"prompt": "upbeat jazz piano, rainy night",
        "audio_A": float[1, S], "audio_B": float[1, S],
        "label": 1}               # 1 = A is better, 0 = B is better

The Bradley–Terry model assumes each clip has a hidden score \(r\), and that the chance A beats B depends only on the difference:

\[ P(A \succ B) = \sigma(r_A - r_B), \qquad \mathcal{L} = -\big[y \log \sigma(r_A - r_B) + (1-y) \log\big(1 - \sigma(r_A - r_B)\big)\big]. \]

Equal scores give 0.5; a gap of 3 gives about 0.95. Adding a constant to every score changes nothing, so a reward has no absolute unit and is only meaningful in comparison. Section 4 depends on this.

CMI-RM (2026)

CMI-RewardBench [6] introduces a benchmark and a reward-model family, as reported [paper]:

  • Encoders: two frozen MuQ-MuLan towers, one for audio and one for text.
  • Two heads: MUS scores musicality; ALI scores alignment with the instruction. About 30M trainable parameters.
  • Two-stage training: pretraining on ~110k pseudo-labeled pairs annotated by Qwen3-Omni [7] (Bradley–Terry loss with label smoothing), then fine-tuning on 4,027 pairs labeled by 31 human annotators.
  • Result: 78.2% agreement with humans on the musicality test set, against 65.8% for Gemini 3 Pro.
class CMI_RM:
    audio_enc = MuQ_MuLan_audio(frozen=True)
    text_enc = MuQ_MuLan_text(frozen=True)
    mus_head = MLP(D, 1)          # [illustrative] head shapes
    ali_head = MLP(2 * D, 1)

    def forward(self, audio, prompt):
        ea, et = self.audio_enc(audio), self.text_enc(prompt)   # [B, D] each
        return self.mus_head(ea), self.ali_head(concat(ea, et))   # musicality from audio alone; alignment from both

def train_step(batch):            # batch holds pairs
    rA_mus, rA_ali = rm(batch.audio_A, batch.prompt)
    rB_mus, rB_ali = rm(batch.audio_B, batch.prompt)
    y = batch.label * (1 - eps) + 0.5 * eps                    # label smoothing: 1 -> 0.95
    loss = bce(sigmoid(rA_mus - rB_mus), y.mus) + bce(sigmoid(rA_ali - rB_ali), y.ali)
    loss.backward()               # only the two heads are updated

The paper also uses it for best-of-N on MusicGen-small and Stable-Audio-Open-small: 2,183 MusicCaps prompts, ten 10-second clips each, \(N \in \{1, 3, 10\}\), scored only after every clip is fully generated. Compared with CLAP best-of-N, the only change is the scoring function, one trained on human preferences. Pruning makes the selection cheaper; a better reward makes it more accurate. I have not seen the two combined.

Code is at github.com/Haiwen-Xia/CMI-RewardBench, and the CMI-Pref datasets are on Hugging Face under CC BY-NC-SA. The paper says weights are released but gives no model repository, so check before planning an experiment around them.

Three scorers, two kinds

CLAP and MuQ-MuLan belong to the same family: dual-tower contrastive models that output one similarity. Qwen3-Omni is a different kind: a generative multimodal LLM that outputs text.

# ===== CLAP (LAION) =====
audio_enc, text_enc = HTSAT(), RoBERTa()        # Swin transformer on mel; general sound data (LAION-Audio-630K)
score = cos(audio_enc(mel(x)), text_enc(p))     # [B]: "do they match?"

# ===== MuQ-MuLan: CLAP's architecture, but the audio tower learns music first =====
targets = MelRVQ(mel(x))           # MuQ: single linear projection + RVQ -> int[B, N, T] as targets
h = Conformer(mask(mel(x)))        # mask time steps, predict the targets (BERT-style), music only, no labels
loss = sum(CE(head[k](h), targets[:, k]) for k in range(N))
score = cos(muq_audio(x), text_enc(p))          # MuLan: contrastive with a text tower, as in CLAP

# ===== Qwen3-Omni: a generative LLM =====
a = AuT(mel_16k_128bins(x))        # ~0.6B audio encoder trained from scratch, mostly ASR; 12.5 Hz, ~80 ms per token
answer = Thinker_MoE(interleave(a, tokenize("Which clip is better?")))   # 30B total, 3B active per token; outputs text

Why can a 30M-parameter head beat Gemini 3 Pro on agreement? A large model is a general judge that was never calibrated to these 31 annotators' taste. CMI-RM's encoders were trained on music, and its heads were fit with Bradley–Terry directly on human choices. Small and specialized beats large and general here.

4. Alignment: DPO

What alignment is for

Best-of-N picks at inference time: every request generates \(N\) songs, at \(N\) times the cost. Alignment changes the generator's weights at training time so good outputs are likely to begin with, and inference can generate one song, or a few.

The objective

With \(\pi_\theta\) the model being trained, \(\pi_{\text{ref}}\) the frozen original and \(r\) a reward:

\[ \max_\theta\; \mathbb{E}_{y \sim \pi_\theta}\big[r(x, y)\big] \;-\; \beta\,\mathrm{KL}\big(\pi_\theta \,\|\, \pi_{\text{ref}}\big) \]

The first term wants high reward; the KL term penalizes drifting from the original model, with \(\beta\) setting the strength. Without it the model finds strange sounds that fool the reward model (reward hacking) and produces only those. Classic RLHF optimizes this with PPO, which samples during training and maintains separate reward and value models: unstable and expensive.

The key step: the objective has a closed-form optimum

The optimal policy can be written down directly [8]:

\[ \pi^*(y \mid x) = \frac{1}{Z(x)}\, \pi_{\text{ref}}(y \mid x)\, \exp\!\big(r(x, y)/\beta\big) \]

Start from the original model and scale each output's probability by \(\exp(r/\beta)\). \(Z(x)\) is the normalizing constant; it cannot be computed, but it is about to cancel. To see why \(\pi^*\) is optimal, rewrite the objective:

\[ \mathbb{E}_{\pi}\Big[r - \beta \log \tfrac{\pi}{\pi_{\text{ref}}}\Big] = -\beta\, \mathbb{E}_{\pi}\Big[\log \frac{\pi}{\pi_{\text{ref}}\, e^{r/\beta}}\Big] = -\beta\, \mathrm{KL}\big(\pi \,\|\, \pi^*\big) + \beta \log Z(x). \]

KL is non-negative and zero only when the distributions match, so the objective peaks at \(\pi = \pi^*\). Now solve for the reward:

\[ r(x, y) = \beta \log \frac{\pi^*(y \mid x)}{\pi_{\text{ref}}(y \mid x)} + \beta \log Z(x) \]

and substitute into Bradley–Terry with a winner \(y_w\) and a loser \(y_l\) for the same prompt. The two \(\beta \log Z(x)\) terms cancel in the difference, which is exactly why "only reward differences matter" was important:

\[ \mathcal{L}_{\text{DPO}} = -\log \sigma\Big(\beta\big[(\log \pi_\theta(y_w) - \log \pi_{\text{ref}}(y_w)) - (\log \pi_\theta(y_l) - \log \pi_{\text{ref}}(y_l))\big]\Big). \]

No separate reward model at training time and no reinforcement learning: an ordinary supervised training loop.

Computing \(\log \pi(y)\) for a codec LM

def seq_logprob(model, text_emb, codes):         # codes: int[B, K, T]
    logits = model(codes_shifted, text_emb)      # float[B, K, T, 2048]
    tok_lp = gather(log_softmax(logits, -1), codes)   # float[B, K, T]: log-prob of the chosen tokens
    return tok_lp.sum(dim=(1, 2))                # float[B]: one number per song

One training step

beta = 0.1                                       # [illustrative] a common value
def dpo_step(batch):                             # codes_w, codes_l: int[B, 4, 1500], two songs per prompt
    lw = seq_logprob(policy, batch.text, batch.codes_w)
    ll = seq_logprob(policy, batch.text, batch.codes_l)
    with no_grad():
        rw = seq_logprob(ref, batch.text, batch.codes_w)
        rl = seq_logprob(ref, batch.text, batch.codes_l)
    margin = beta * ((lw - rw) - (ll - rl))      # [B]
    loss = -logsigmoid(margin).mean()
    loss.backward()

The gradient pushes the winner's probability up and the loser's down, relative to the reference model, weighted by \(\sigma(-\text{margin})\). The more wrong the model currently is (very negative margin), the harder it pushes; once a pair is ranked correctly it barely moves.

Where preference data comes from

  • Human labels: MusicRL used about 300,000 pairs, as summarized by Herremans and Roy's position paper [9].
  • Reward-model labels (RLAIF): generate two songs per prompt, let a reward model such as CMI-RM pick the winner, train DPO on the pairs. DiffRhythm+ applies DPO to whole-song generation against several scores, including SongEval and Audiobox-aesthetic [9].
  • HeartMuLa builds pairs from three rewards, trains one DPO model per reward and merges their weights, as above [3].

5. How the three connect

generator (§2) --N songs--> reward model (§3) --+--> at inference: keep the best = best-of-N
                                                 +--> at training: winner/loser pairs -> DPO (§4) updates the generator

How far does best-of-N move the output distribution? The commonly quoted formula, shown by Beirami et al. [10] to be an upper bound, is

\[ \mathrm{KL}\big(\pi_{\text{BoN}} \,\|\, \pi_{\text{ref}}\big) \le \log N - \frac{N - 1}{N}. \]

At \(N = 8\) that is about \(2.08 - 0.875 \approx 1.2\) nats. Doubling \(N\) adds only about \(\log 2 \approx 0.69\) nats while doubling the cost, so best-of-N hits diminishing returns quickly. That is the case for moving preferences into the model at training time.

Put together: pruning lowers the cost of best-of-N, a preference-trained reward model makes its choice more accurate, and DPO shrinks the \(N\) you need at all. The open question in between is whether a reward model's score on the first ten seconds predicts its score on the finished clip. That has to be measured before pruning on it.

Appendix: why classifier-free guidance works

In one sentence: each step amplifies the part of the prediction that is specific to the prompt. By Bayes' rule,

\[ \log p(y \mid c) = \log p(y) + \log p(c \mid y) + \text{const}, \]

where \(p(y)\) asks "does this sound like music?" and \(p(c \mid y)\) is an implicit classifier: "having heard this, how likely is the prompt to be \(c\)?" That classifier never needs training, since \(\log p(c \mid y) = \log p(y \mid c) - \log p(y) + \text{const} = \ell_c - \ell_u\), hence classifier-free [11]. Weighting it by \(\gamma\):

\[ p_\gamma \propto p(y)\, p(c \mid y)^{\gamma} \quad\Longrightarrow\quad \log p_\gamma = \ell_u + \gamma\,(\ell_c - \ell_u). \]

\(\gamma = 0\) is unconditional, \(\gamma = 1\) ordinary conditional generation, and \(\gamma > 1\) follows the prompt harder (MusicGen's default is 3). It works on logits directly because the log-sum-exp term is the same constant for every token and cancels in the softmax. A worked example with \(\gamma = 3\): \(p_u = [.5, .3, .2]\) and \(p_c = [.7, .2, .1]\) give a guided distribution of \([.92, .06, .02]\).

Training drops the prompt for 10–20% of examples, so one model learns both modes. The costs: twice the rows per step, less diversity and more artifacts as \(\gamma\) grows, and applying it token by token is only an approximation of guiding the whole sequence. Finally, rewriting \(p_\gamma\) shows the link to DPO:

\[ p_\gamma \propto p(y \mid c) \cdot \exp\!\Big(\log p(c \mid y) \big/ \tfrac{1}{\gamma - 1}\Big), \]

the same form as \(\pi^* \propto \pi_{\text{ref}} \exp(r/\beta)\) with \(r = \log p(c \mid y)\) and \(\beta = 1/(\gamma - 1)\). CFG is inference-time alignment whose reward is the model's own implicit classifier.
