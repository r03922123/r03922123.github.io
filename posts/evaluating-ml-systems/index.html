Evaluating ML systems: classification, ranking, search and generative models

October 31, 2026 · 8 min read · evaluation · experimentation · reference

A model metric is only useful if moving it moves something people care about. This reference follows the same chain for four kinds of system: business value → product metric → model metric, then how to test offline and online, and the problems that tend to break each step. The formulas are written out, and the metric code at the end runs as is.

The chain from value to metric

Start from what one more correct prediction is worth, and work down:

  • Business value is money or risk: revenue per recommendation, fraud losses avoided, support cost saved.
  • Product metrics are what users do: clicks, watch time, retention, tasks resolved without escalation.
  • Model metrics are what you can compute offline: precision at a threshold, NDCG, calibration error.

Each link is a hypothesis. A gain in offline NDCG is worth something only if it raises a product metric online, and that only if the product metric tracks value. Most evaluation failures are one of these links quietly breaking.

Classification

Pick the operating point first

A deployed classifier runs at one threshold, so threshold-free summaries hide what users will get. Fix the constraint the product actually imposes, then report the other side of the trade-off at that point: precision at a recall floor set by policy, or recall at a review capacity of \(n\) items a day.

\[ \text{precision} = \frac{TP}{TP + FP}, \qquad \text{recall} = \frac{TP}{TP + FN}. \]

Threshold-free summaries, and when to use which

  • ROC AUC is the probability that a random positive scores above a random negative. It ignores class balance, which makes it stable across datasets but optimistic when positives are rare: a model can have a high ROC AUC and still bury every true positive under false alarms.
  • PR AUC (average precision) is dominated by the positive class, so it moves when performance on rare positives moves. With positives under a few percent, it is the more honest summary.

Calibration

If scores are used as probabilities (for expected-value decisions, or combined with other models), check that a score of 0.8 means right about 80% of the time. Expected calibration error bins predictions by confidence and averages the gap between confidence and accuracy, weighted by bin size [1]:

\[ \mathrm{ECE} = \sum_{b=1}^{B} \frac{|S_b|}{n}\, \big|\, \mathrm{acc}(S_b) - \mathrm{conf}(S_b) \,\big|. \]

Modern networks are often over-confident; temperature scaling on a held-out set is a cheap first fix [1].

Where it breaks

  • Label scarcity and rarity. When positives are rare, the test set holds few of them and every metric is noisy. Report confidence intervals, and mine hard negatives so the training set teaches the boundary.
  • Labels that disagree. If two experts disagree on 20% of borderline cases, no model can be measured above that ceiling. Measuring inter-rater agreement comes before measuring the model.

Recommendation

Business and product metrics

Write down the value of one more relevant recommendation. For a shop it is roughly \(P(\text{click}) \cdot P(\text{buy} \mid \text{click}) \cdot \text{average order value}\); for ads it is impressions × revenue per thousand impressions; for a subscription, the effect on retention times customer lifetime value. The product metrics that follow are session watch or dwell time, revenue per user, retention, and catalog coverage, the share of the catalog that gets recommended at all.

Model metrics

  • Recall@k: of the items the user went on to engage with, the fraction that were in the top \(k\). It is the natural metric for a retrieval stage, whose job is to not lose good candidates.
  • NDCG@k [2]: rewards putting the most relevant items highest, with a logarithmic discount by rank, normalized by the best possible ordering: \[ \mathrm{DCG@}k = \sum_{i=1}^{k} \frac{\mathrm{rel}_i}{\log_2(i + 1)}, \qquad \mathrm{NDCG@}k = \frac{\mathrm{DCG@}k}{\mathrm{IDCG@}k}. \] A common variant uses gain \(2^{\mathrm{rel}_i} - 1\) to weight highly relevant items more.
  • MRR [3]: the reciprocal rank of the first relevant item, averaged over queries. Right when the user needs one good answer.
  • Coverage and diversity: offline accuracy rewards recommending what is already popular, so track these alongside it.
  • Calibration of predicted click rates matters whenever scores feed an auction or a blend with other objectives.

Where it breaks

  • Logged data is biased by the old system. Offline labels are clicks on what the previous model chose to show, at the positions it chose. A new model that surfaces different items looks worse offline simply because those items were never shown. See position bias for corrections with inverse propensity weighting.
  • Feedback loops. A model trained on its own output narrows over time. A small exploration budget and a long-lived holdout served by a simple heuristic give a baseline that model changes cannot drag along.

Search

Search differs from recommendation in having an explicit query, which makes graded relevance judgments possible: annotators rate query–document pairs (say 0–3), and those judgments are reusable across models.

  • NDCG@10 on judged pairs is the standard offline metric, because graded labels are what DCG's gain was designed for.
  • MRR for navigational queries, where one correct result is the answer.
  • Precision@k for the first screen, since that is what users read.
  • Zero-result rate and query reformulation rate are product signals of failure that need no labels.

The trap is unjudged documents: a new ranker retrieves documents nobody rated, and counting them as irrelevant penalizes exactly the novelty you wanted. Judge the new top results before comparing, or report how many results were unjudged. Online, compare rankers with interleaving, which reaches a verdict with far less traffic than a split test [4].

Generative systems

Product metrics

These depend heavily on the application: task resolution rate, how often a human has to take over and how long that takes, response latency, satisfaction, and safety incidents.

Model metrics: a portfolio, not a number

There is no single scalar for generation quality, so measure several things at once:

  • Overlap with references. BLEU [5] and ROUGE [6] count shared n-grams; BERTScore [7] and BLEURT [8] compare meaning with learned models. All need references, and open-ended outputs have many valid answers that share few words with any one reference.
  • Behavior. Factuality and hallucination rates, toxicity and policy classifiers, and diversity, for example self-BLEU between a model's own samples [9], where higher means more repetitive.
  • Preference. Pairwise win rate against a baseline, from people or from an LLM judge. LLM judges agree with people reasonably often but have known biases toward position, length and their own style [10], so swap orders and spot-check against human labels.
  • Audio and music. Fréchet Audio Distance [11] compares the distribution of generated audio to real audio in an embedding space; CLAP score [12] measures how well a clip matches its text prompt. Neither measures whether people like it, which is the subject of my post on judging text-to-music.

Testing

Offline, build a golden prompt set that covers the main intents, languages, hard edge cases and known policy risks, with several reference answers or pairwise human rankings per prompt. Online, run the candidate in shadow mode first: it answers in the background, invisible to users, so you can log latency, cost and automated quality scores. Then ramp traffic in an A/B test while watching safety dashboards next to product metrics, and keep a small group on the previous model as a standing baseline for drift.

Where it breaks

  • Human review is slow and expensive. Split quality into dimensions (fluency, factuality, style) and send only uncertain cases to experts, with automated checks screening the rest.
  • Hallucination is worst on rare prompts, so test suites must deliberately include tail queries, and safety detectors should be tuned for few misses rather than few false alarms.
  • Test sets go stale. Prompts drift with users; refresh evaluation sets from recent traffic, and version the rubric along with the model.

Online testing, done carefully

For a click-through-rate test with \(n_A\) and \(n_B\) independent trials, the two-proportion z-test pools the rate under the null hypothesis of no difference:

\[ \hat p = \frac{c_A + c_B}{n_A + n_B}, \qquad z = \frac{\hat p_B - \hat p_A}{\sqrt{\hat p (1 - \hat p)\left(\frac{1}{n_A} + \frac{1}{n_B}\right)}}. \]

\(\hat p(1 - \hat p)\) is the variance of one Bernoulli trial; the square root of the whole expression is the standard error of the difference. With 500,000 sessions per arm and CTRs of 2.00% and 2.10%, the relative lift is 5.0%, \(z = 3.53\), and the two-sided p-value is \(4 \times 10^{-4}\).

Three ways this goes wrong in practice:

  • The unit of analysis is not the unit of randomization. If users are randomized but the metric is clicks per session, sessions from one user are correlated and the formula above understates the variance. Use the delta method for ratio metrics, or bootstrap over users [13].
  • Peeking. Checking significance every day and stopping at the first \(p < 0.05\) inflates false positives far beyond 5%. Fix the sample size in advance, or use a sequential test designed for it.
  • Sample ratio mismatch. If a 50/50 split arrives as 50.6/49.4 over a million users, something in assignment or logging is broken, and the result should not be trusted until it is found [13].

Metric code

import math


def dcg(rels):
    return sum(rel / math.log2(i + 2) for i, rel in enumerate(rels))   # rank 1 -> log2(2) = 1


def ndcg_at_k(rels, k):
    ideal = dcg(sorted(rels, reverse=True)[:k])
    return dcg(rels[:k]) / ideal if ideal > 0 else 0.0


def mrr(ranked_lists):                   # each list: 1 if relevant else 0, in ranked order
    return sum(next((1 / (i + 1) for i, r in enumerate(rels) if r), 0.0)
               for rels in ranked_lists) / len(ranked_lists)


def recall_at_k(rels, k, n_relevant):
    return sum(1 for r in rels[:k] if r) / n_relevant


def two_proportion_z(clicks_a, n_a, clicks_b, n_b):
    p_a, p_b = clicks_a / n_a, clicks_b / n_b
    p = (clicks_a + clicks_b) / (n_a + n_b)              # pooled rate under H0
    se = math.sqrt(p * (1 - p) * (1 / n_a + 1 / n_b))
    return (p_b - p_a) / se, (p_b - p_a) / p_a           # z, relative lift


assert ndcg_at_k([3, 2, 1, 0], 4) == 1.0                 # already ideal
assert round(ndcg_at_k([0, 1, 2, 3], 4), 3) == 0.614     # fully reversed
assert mrr([[0, 1, 0], [1, 0, 0], [0, 0, 0]]) == 0.5     # (1/2 + 1 + 0) / 3
assert recall_at_k([1, 0, 1, 0, 0], 3, n_relevant=4) == 0.5
z, lift = two_proportion_z(10_000, 500_000, 10_500, 500_000)
assert round(z, 2) == 3.53 and round(lift, 3) == 0.05
